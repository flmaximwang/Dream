# dream 方法本体（S1–S10 的完整做法）

本文件是 `SKILL.md` 的下一层：每一步的完整做法与判据。凡是与**某个 agent 绑定**的机制（容器判据、
安装/更新/卸载命令、判官服务接线、私有路径），这里一律写成「适配层提供 X」——具体值在那个 agent 的
适配技能里（Hermes = `dream-hermes-routing`）。

## s1 · 枚举

```bash
python3 -B skills/dream/scripts/sweep-plan.py scan \
  --profile <profile> --packs-root <主技能根> --out <scratch>/sweep-<date>
```

候选判据 = **容器**，不是目录名。适配层给三件事：① 容器定义（哪些 skill 已有仓库归属 ⇒ 不是候选）；
② 技能根清单（可能有多个根）；③ 包索引（本机可当落点的目录名）。

产出（全在 `--out` 里）：

| 文件 | 内容 |
|---|---|
| `inventory.tsv` | 全表：skill / category / 容器 / 路径 / 内容 sha256 |
| `judge-input.json` | **冻结**的候选表：id / skill / category / path / `skill_md` 绝对路径 / `refs` 清单 / 正文字节数 |
| `judge-input-bodies.json` | 同一批，另外把正文内联（给只会看文本的判官） |
| `packs.json` | 每个落点目录：路径 / 三段式标识符 / 分支 / 技能清单 / 已装成员 / 是否空壳 / 是否可路由 |
| `answer-space.json` | 判官的**落点空间**：全部目录名 + 按轴分好的两组 + 可路由名单 + 新包命名式 |
| `pack-index.txt` | 可路由包的各条 `category/name: desc` |

🔴 两点硬约束：

1. **没有类目层的候选一条都不许留**：`skills/<名字>/SKILL.md` 直接躺在 skills/ 下 = 形状缺口
   （列表里 category 列空白）。脚本标 `no_category=true` 并单独报数；判官对这类行**必须同时给出目标类目**。
2. **落点空间是「全部候选目录名」**，不是「有 remote 且非空壳」的那一小撮：本机实测落点 290 个目录名，
   其中只有 33 个可路由。可路由**只决定这个落点以后能不能装回来，不限制它能否当落点**——空壳由 writer
   在写入前补 remote。`.git` 是**文件**（不是目录）的目录不是包（那是别的 clone 的 worktree），脚本过滤掉。

## s2 · 路由判断

落点由**独立判官**给，不由主 agent 给（主 agent 刚枚举完，对「这条像哪个包」已有先入之见）。

**两轴先判。** 第一步是二选一，不是挑名字：这条技能的**主语**是「某个软件/工具」，还是「一类任务/学科/项目」（主题）？

- 工具轴 → `AgentSkill-Using<软件名>`：先在存量名里挑，**本机没有这个工具**才新造。
- 主题轴 → 存量主题名里挑（少而合：一主题一包）；都不合适才新造主题名。

`answer-space.json` 的 `tool_dirs` / `topic_dirs` 就是这两组的现成清单（脚本产出，别手抄）。

**三段问法**（一段一问，不许合成一段）：① **轴** —— 主语是工具还是主题？② **落点** —— 该轴里哪个目录名
（要新包就答 `new` 并给轴与名字）；③ **落点技能** —— 落点是已有目录时，并入它已有的哪条技能，还是 `__new__`。

**verdict 形状**（一行一条 JSONL）：

```json
{"id":"P12","dest":{"kind":"existing","repo":"AgentSkill-UsingGit","dest_skill":"__new__","action":"move"},
 "why":"…","evidence":"正文原句：「…」或 file:line","confidence":0.82,"source":"agent"}
{"id":"P13","dest":{"kind":"new","axis":"tool","topic":"Jev","personal":false,
 "boundary":"不吃 Cline/Cursor 这类编辑器的接入"},
 "why":"…","evidence":"…","confidence":0.8,"source":"agent"}
```

- `kind:"existing"`：`repo` 必须是 `answer-space.json` 里出现过的**目录名**；`dest_skill` 必须是那条目录
  **已有**的技能名或 `__new__`（脚本拿 `packs.json` 核对，编出来的名字当场拒收）；`action` ∈ `move` / `merge` / `strengthen`。
- `kind:"new"`：`axis` ∈ `tool|topic`、`topic` 非空、**`boundary` 必填**（这个包**不吃**什么）、`personal` 布尔。
  按 `AgentSkill-Using<topic>` / `AgentSkill-<topic>` 命名；归一化后撞上已有目录名 → **复用那个仓库**（不建孪生目录）；
  **同一 topic 的多条合并进一个包**。
- `personal:true` 且该 topic 只有 1 条 → 私人仓库，建库那一步才 `gh repo create --private`，汇报里单列。

🔴 **没有 `__stay_local__`**：每条候选都必须有落点。判不出来不是「留本地」，是**没判完**。

🔴 **严禁偷懒判法**（用户原话：「不能有机械、偷懒、不基于 skill 内容的判断（简单从名称提取关键词、
简单根据 profile 合并等都属于偷懒行为）」）：① **判官必须读 SKILL.md 全文**（含正文点名的 `references/`），
不许只看 `name` / `description` / `category`；② **每个落点必须回一条正文证据**（正文原句，或 `file:line`），
`evidence` 空的 verdict 视为没判；③ **禁止按类目批量套模板**——每条独立判，同类目下不同技能可以落不同包，
允许新包只吃 1 条。

**走哪条路（判官接线）**：适配层给「判官在哪 / 怎么探活 / 不可用时怎么降级」。通用三条：
① 先探活，再出题；探活失败（无凭据 / 区域不可用 / 超时）**直接走降级**，别重试到超时；
② 判官在线 → 把 `judge-input-bodies.json` 当 `state` 分块出题，落 `verdicts-<judge>.jsonl`，
**每条记下回复里的 `model` 字段**才算真机答案；
③ 判官不在 → 派分类子代理，**每 8–12 条一个**（判官要读全文，一条比只给 name+desc 贵得多），
落 `verdicts-task-N.jsonl`。
④ **标注纪律**：只有带 `model` 字段的算判官答案；子代理/人工填的一律 `source: agent`，两组数字分开写。

判据：`merge` 覆盖率必须 100%，且没有任何 `dest.repo` 落在 `answer-space.json` 之外。

## s3 · 交叉审计

只跑「落点 = 已有技能」的行。派一个子代理读**源 skill 整个目录 + 接收技能整个目录**，按 claim
（表头 / 实测数字 / 命令旗标 / 源路径）逐条 grep，产出两张清单：

- **already there** —— 每条带接收侧的 `file:line`；
- **net-new** —— 接收侧确实没有的。

和一个建议：`merge`（把净值折进去）/ `new`（净值和边界都不同，另起一条）/ `strengthen`（重叠少但话题相邻
⇒ 两边头部各加一句界限声明）。**先证明再动手**是本步唯一的硬要求。

## s4 · 自动决议

```bash
python3 -B skills/dream/scripts/sweep-plan.py merge --dir <scratch>/sweep-<date> --profile <profile>
```

`plan.md` 按落点分组（新包 / 复用已有目录 / 已有包三类），`resolved.json` 是逐行的机器可读决议，
`install-cmds.sh` 是 s7 的命令清单（脚本按 lock 证据生成，**不执行**）。

主 agent 按 `SKILL.md`「无人值守」一节的规则**逐行决议、不等人**。汇报里分开写：① 明确归位
② **拟新建的包**（只报不建）③ 判官判了新包但归一化后撞上已有目录 → **复用**（单列，因为它改的是既有仓库）
④ 上游自有仓库的行（单列）；另把**没有类目**的行单列（写清落进包的哪个类目，或该挪进哪个**现有**类目）。
要人拍板的事写进汇报即可，**不许停在那里等**。

## s5 · 写入

**每个目标包一个 writer 子代理**，包内串行、跨包并行（上限 10，超过就分波）。writer 的活：

1. `git fetch` + `git status`：**profile 副本比仓库新时先逐字节回移植**（那是别的会话在途的工作，单独一个提交）。
2. 按包形状写：frontmatter 只留 `name` + `description`、references 用 `<skill>-<topic>.md`、
   正文末尾带那两行 Generated by Scripts 注释标记。
3. 包内脚本依赖按 `../../<兄弟技能>/scripts/` 定位。
4. 跑生成段脚本 → 跑包校验脚本 → 预测扫描 verdict（非 `safe` 先按扫描闸手册改写形态；`dangerous` 的
   revision 装不上，`--force` 也覆盖不了）。
5. `git add skills/<name>`（**pathspec**）→ commit → `git push origin <sha>:main`。

writer 必须回：commit sha、推出去的 sha、扫描 verdict、`git diff --cached --stat`。
**一次跑不完就在每条技能上各自提交**：长活被截断时，已提交的那些就是可回读的成果。

**落点是新包时多一步：先把仓库建起来**——建库（幂等：已存在就复用）→ **立刻把 remote 换成 SSH**
（CLI 建出来常是 https，裸 push 会卡在凭据提示直到超时）→ **README 是交付物的一部分**（索引表 +
三段式安装命令 +「当前状态：装 / 不装」那一段）→ 按 `skills/<name>/SKILL.md` 布局写第一条技能 →
**首推之前必须扫出 `safe`**。但**建仓库这一步只在这次调用被点名要建包时才做**：无人值守下名字先落进
汇报的「拟建」段，用户点名后再建。

## s6 · 独立验证

**一条与所有 writer 都不同的只读子代理**，对 `plan.md` 的**每一行**核一遍，逐行 PASS/FAIL：

- 交付的目录在 clone 里存在且与计划一致；
- `git log --oneline -1 origin/main` 就是 writer 报的 sha；
- `diff -rq <clone>/skills/<name> <安装副本>` 为空；
- 安装来源标识符（lock / manifest）指向该 repo；
- 从**装好的那份**用 `python3 -B` 跑一次脚本。

FAIL 的行回 s5 修，不静默放过。

## s7 · 整包重装

```bash
sh <scratch>/sweep-<date>/install-cmds.sh   # 先数一遍条数写进汇报：一包 20 行 = 20 个 prompt 行，是代价
```

先 `install` 新成员，再 `update` 改动过的与**本包既有成员**（整包重装）。回读三件（同 s6 判据）。
适配层的安装命令与其坑见 `dream-hermes-routing`。

## s8 · 退役与汇报

退役**只在回读通过之后**（这是自动闸，不是人闸）：先 `tar czf` 备份并把备份路径写进汇报，再删本地副本；
回读有 FAIL 的行先修，修不动的那行跳过（**副本不删**）。

汇报四段：枚举数 · 判定表 · **每行对应的证据**（sha / verdict / diff / check 原文）· ≤3 条要人拍板的事
（每条：要你定什么 / 为什么只能你定 / 我的建议与代价）——不等人回话，本批次到此结束。

## s9 · 全库去重 + 无类目归位

```bash
python3 -B skills/dream/scripts/sweep-plan.py dedupe \
  --profile all --packs-root <主技能根> --fix-no-category \
  --backup <备份目录>
```

去重三种情况：**SKILL.md 相同** → 直接删 local（包是 source of truth）；**不同且 local 有旧 profile 路径引用**
→ 先回移植到包，再删 local；**不同且无路径修复** → 包更新，直接删 local。

无类目归位（`--fix-no-category`）：候选类目**只能是该 profile 自己已有的类目**；按技能名关键词匹配现有类目；
匹配不上就报「需要新类目」，**不自动归入 misc**。

🔴 **`not_in_pack > 0` 是硬错误（exit 5）**：判据是 **local 必须为 0**——还有 local skill 没有任何仓库归属，
就说明这批没做完，不许当一句脚注收尾。

🔴 **先 `--dry-run` 看一遍**，确认数字合理再真跑。备份落在 `--backup` 指定的目录。

## s10 · 合并 / umbrella（把一簇窄 skill 收成一条类级技能）

**触发**：同一类任务上有 **2+ 条成员**，且维护者会为这一类起一个名字。判据来源沿用 s2–s4 的分工
（判官定落点、交叉审计核接收侧、人工闸放行）。自治维护已全局关闭（`auxiliary.background_review.enabled=false`
+ `curator.enabled=false` + `curator.consolidate=false`）⇒ 这一节的动作**只在有人在场的会话里做**。

**合法合并只有三步，顺序不可换，每一步留一条台账**。台账 = `~/.hermes/skills/.curator_ledger.jsonl`，
一步一行，`action` 就是下面这三个动作名（前台 `actor` = `agent`）：

1. **吸收** —— `skill_manage action=write_file name=<umbrella> file_path=references/<topic>.md`
   （按题目命名；模板进 `templates/`、脚本进 `scripts/`）。先让内容在 umbrella 里**落地并蒸馏**：
   吸收来的正文变成规则（命令式 + 一句 why），同一课讲两遍的合成一条，事故叙述 / PR 号 / 日期丢掉。
   把文件原样挪进 `references/` 是归档，不是合并。
2. **清源** —— `action=remove_file` 删源里已经搬走的那份原文（`file_path` 用源目录内的相对路径）。
   这一步两边都还在，可回读核对，先别急着销源。
3. **销源** —— `action=delete name=<源> absorbed_into=<umbrella>`。**`absorbed_into` 必填**：不带
   （或给空串）时 `_curator_consolidation_delete_guard`（`tools/skill_manager_guards.py:232`）当场拒绝
   （fail-closed）；`_delete_skill`（`tools/skill_manager_tool.py:559`，校验在 :567–572）另要它指向
   **已存在**的技能、且不等于被删的那个 ⇒ 所以第 1 步必须真的先落盘。

**前 57 字符是产出**：umbrella 的 description 必须把**触发类**留在前 57 字符窗口内。系统提示里的技能索引
按 57 字符截断（`agent/curator.py:299`、`tools/skill_manager_tool.py:830`），而检索按 description 匹配、
不按名字 ⇒ 触发词飘到窗口外就**静默失效**（新旧触发词一起丢）。形状：`Use when <触发类>…` 打头，
行为描述往后放。

**前台 delete 是硬删**：`.archive/` 那条可恢复的路只在后台复盘通道走
（`tools/skill_manager_tool.py:580`：`if _is_background_review()` 才 `archive_skill`）；人在场时走
`shutil.rmtree`。所以动手前先 `hermes curator backup` 留一份快照，别指望 `.archive/`。

**反例（不要做的事）**

- **不带 `absorbed_into` 就 `delete`**：后台通道当场被 `_curator_consolidation_delete_guard` 拒（技能保持
  active）；人在场时它**删得掉**，但台账上只留一条没有接收方的 `delete` —— 后人查不出内容去哪了。
  正确顺序是先写 umbrella 再销源：接收方在那时已经存在、可记。
- **用 shell `mv` / `cp` 搬 skill 内容**：`skill_manage` 之外的写入**不进台账**，
  `.curator_ledger.jsonl` 里没有对应的 `write_file` / `remove_file` 行，回读时无从对账
  （S5 的「不要用 `mv` 当迁移」是同一件事的批量版；包是 source of truth，副本只在回读之后退役）。
  搬运只走 `skill_manage`。
